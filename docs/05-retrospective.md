# 05 - 复盘（Retrospective）

## 最难的三个问题

**1. "预算判断"放在哪一层？**
最初的设计诱惑是让 `estimate_cost` 直接返回 `within_budget` 字段，甚至让工具在超预算时自动返回更便宜档位。但这样"重规划"就成了工具层的预设分支——模型只是转发结果，恰恰落入试卷"固定条件分支不视为 ReAct"的否定项。最终把 `estimate_cost` 收敛为**只返回费用事实**（total/breakdown），对比预算、决定换档、计算缺口全部由模型完成。代价是 Mock 策略要自己算缺口（8 − 5 = 3），收益是 `budget-overrun` 的 Trace 里能看到真实的决策依据"观察到 standard 档估算 12 超出预算 10，改选 lite 档"。

**2. 失败步骤续跑，如何做到"保留成功、不虚报失败"？**
题目明确"部分成功时保留已成功步骤结果""不能把失败步骤记为成功"。难点在于步骤状态如果由"最终结果"反推，失败就会被成功掩盖。最终让步骤状态**按实际观察逐条记录**：失败保留 `failed`，重试成功另起一条 `success`——`tool-failure` 的 steps 里因此同时存在 `generate_script: failed` 与 `generate_script: success` 两条记录。过程中发现一个真 bug：`save_plan` 的成功状态是 `saved/duplicate` 而非查询类工具的 `ok`，步骤状态被误标为 `failed`，测试失败后把成功状态集合改为 `{ok, saved, duplicate}` 才修正。这也验证了"失败不虚报"必须靠断言盯住，而不是靠实现自觉。

**3. "重试一次"的边界怎么划，才不算无脑蛮干？**
加分项要求"工具失败时调整计划"，但不是所有失败都值得重试：检索返回 `topic_not_found` 是确定性失败（素材库里没有这个主题），重试只是浪费步数；瞬时故障（注入的 `transient`）重试一次才合理。最终按失败类型分流：`topic_not_found` 直接如实终止；其他失败用同一参数重试一次；连续两次失败则终止并保留已成功步骤。重试的依据写在决策依据里（"上次返回失败（…），按失败处理策略重试一次，保留已成功步骤"），可审计。

## 学习收获

- **事实与判断分离是动态决策的根基**：工具只给事实（费用、占用、成败），判断（超没超预算、换不换档、值不值得重试）留在模型侧——这既是 ReAct 真实性的来源，也让每一步都能被 Trace 审计。
- **评测先行于实现**：先把验收点 + 3 条红线写成可执行断言，再让实现向断言收敛；`save_plan` 成功状态误标 bug 就是测试先红、实现后绿的。
- **结构比约束可靠**：防超预算入库靠"红线断言 + 幂等键在工具层"，防失败被掩盖靠"状态按观察逐条记录"，都优于在 Prompt 里写"请不要虚报"。

## 下一步（按优先级）

1. **接入真实模型验证**：用 `AGENT_MODEL=api` 跑通同一组验收用例，对比 Mock 与真实模型的 Trace 差异；为 API 模式增加输出 JSON 校验与格式漂移重试。
2. **截止时间可行性推演**：利用 `cost_table.json` 中 tool_fees 的耗时字段，把 deadline 从"信息完整性校验"升级为真正的时间约束（预计完成时间 > 截止时提前降档或如实报告）。
3. **分项预算协商**：超预算时除了换档，支持"砍分项"（如去掉渠道推广）的重规划路径，与换档组合成更大的决策空间。
4. **pass^k 稳定性**：同一用例重复运行 k 次验证真实模型下的稳定性（对 Mock 无意义，对 API 模式必要）。
5. **方案确认回流**：保存的方案增加人工确认/驳回状态，形成 HITL 闭环。
